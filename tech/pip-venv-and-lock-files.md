# pip, virtual environments and lock files (with uv)

## What it is

- **pip** installs Python packages (libraries and tools) from the Python Package Index (PyPI), the public download site.
- A **virtual environment** (venv) is a folder, here `.venv/`, holding its own copy of the Python interpreter's package area. Packages installed into it do not touch the rest of your computer, and two projects can use different versions.
- A **lock file** lists every package the project needs, directly or indirectly, each at one exact version, with a **hash** (a fingerprint of the file) so pip can refuse a package that was changed.
- **uv** is a fast tool from Astral that can compute such a lock file. It was used once, to write the two lock files. You do not need it to use the repository.

## Why this repository uses it

The template asks for dependencies pinned with a lock file and checked by an audit. With hashes, the packages you install today are the exact bytes the author tested, and `pip-audit` can check them for known vulnerabilities (`tech/pip-audit.md`).

## Where it appears

| Path | What it does |
| --- | --- |
| `requirements.lock` | What the programs need to run (`kafka-python`). |
| `requirements-dev.lock` | Run-time packages plus the development tools (pytest, ruff, mypy, ...) and everything they need: about 890 hash lines. |
| `pyproject.toml` | The source of truth: the list the locks are computed from. |
| `Makefile` (`$(STAMP)` rule) | Creates `.venv` and installs from the lock file. |
| `Dockerfile` | Installs `requirements.lock` into the image. |
| `.gitignore` | Keeps `.venv/` out of git. |

## How it works underneath

`python -m venv .venv` makes the folder with a `bin/` directory holding `python` and `pip` that are tied to it. `.venv/bin/pip install ...` puts packages in `.venv/lib/python3.13/site-packages/`. Nothing needs "activating": calling `.venv/bin/python` directly uses the environment, and that is what the Makefile does.

An **editable install** (`pip install -e .`) does not copy the project's code; it leaves a small pointer file so Python imports `order_events` straight from `src/`. Changes show up at once.

## Walkthrough of this repository's use

```make
$(STAMP): requirements-dev.lock pyproject.toml
	$(PYTHON) -m venv $(VENV)
	$(VENV)/bin/pip install -q --require-hashes -r requirements-dev.lock
	$(VENV)/bin/pip install -q --no-deps -e .
	touch $@
```

- `$(PYTHON) -m venv $(VENV)`: create the environment with the chosen interpreter.
- `pip install -q --require-hashes -r requirements-dev.lock`: install everything in the file. `-q` is quiet. `--require-hashes` makes pip refuse any package without a matching hash, and also requires every package to be pinned with `==`.
- `pip install -q --no-deps -e .`: install this project itself in editable mode. `--no-deps` because the lock already installed the dependencies. After this, `import order_events` works and the commands from `[project.scripts]` (like `order-events-produce`) appear in `.venv/bin/`.

The lock file's first lines:

```text
# This file was autogenerated by uv via the following command:
#    uv pip compile pyproject.toml --universal --generate-hashes --python-version 3.12 -o requirements.lock
kafka-python==3.0.12 \
    --hash=sha256:4ccda3616b9aa5c353d74a97f2770d6cd1b950890d77ab0e8890e09a48eeed65 \
    --hash=sha256:67add72052e3ad0c37ed9963ebe2b1696adc7f063c64eaf19862c21b69a64a18
    # via kafka-order-events (pyproject.toml)
```

The header records the command that produced it: `uv pip compile pyproject.toml --universal --generate-hashes --python-version 3.12 -o requirements.lock`. `--universal` makes one file that works on Mac and Linux, `--generate-hashes` adds the fingerprints, `--python-version 3.12` makes it valid for Python 3.12 and newer. Each package is `name==version` followed by one `--hash=sha256:...` per downloadable file. The line `# via kafka-order-events (pyproject.toml)` says why the package is there.

To refresh the locks after editing `pyproject.toml`: run the `uv pip compile` command from the header (and the same with `--extra dev -o requirements-dev.lock`).

## Try it yourself

1. `.venv/bin/pip --version` prints the pip version and the path inside `.venv`.
2. `.venv/bin/pip show kafka-order-events` shows `Editable project location:` pointing at the repository.
3. `.venv/bin/pip list | wc -l` prints about 47 (packages plus two header lines).
4. `grep -c '^[a-z]' requirements.lock` prints `1`: the only run-time dependency.
5. `ls .venv/bin` shows `python`, `pip`, `pytest`, `ruff`, `mypy` and `order-events-produce` among others.

## Mistakes people make

- Installing into the system Python. A venv avoids version clashes.
- Editing a lock file by hand. Recompute it.
- Committing `.venv/`.
- Leaving dependencies as ranges. Ranges give different installs next month; the lock does not.
- Expecting `--require-hashes` to work with a package that has no pin: pip stops with an error.

## Check yourself

1. Why a virtual environment? *Packages for one project stay separate from everything else.*
2. What does a hash in a lock file protect against? *A package whose bytes changed since the lock was made.*
3. What does `-e .` do? *Installs the project so imports read directly from `src/`.*
4. Which file lists the packages the author chose by hand? *`pyproject.toml`.*
5. Do you need uv to use this repository? *No; only to recompute the locks.*
